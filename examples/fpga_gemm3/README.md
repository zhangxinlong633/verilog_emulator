# ASIC 风格矩阵乘法加速器（目录名 `fpga_gemm3`）

## 概述（先看这个）

矩阵乘法（把两张数字表按规则乘成一张新表）是 AI、图像、科学计算里最吃算力的基本动作之一。大模型「蹦出一个字」，背后往往要做很多次这种乘法。

本目录用 **ASIC / NPU 的思路** 描述一台专用矩阵乘引擎（固定乘法器阵列 + 大矩阵分块），并用 Verilog 在 `vs` 里做可跑的小规模验证。目录仍叫 `fpga_gemm3`，只是历史路径名；**产品叙事按 ASIC 档讨论主频与硅片成本**（也可综合到 FPGA 上做原型，但默认假设不是「只能跑 100 MHz 的 FPGA 实验」）。

可以概括成三句话：

1. **造一台专用小机器**：片上摆满乘法器，专门算「一块」固定大小的矩阵（叶尺寸 **T**，常见 T=32，也可讨论 T=64）。  
2. **大矩阵切成小块再算**：超过 T 的矩阵（比如 1024×1024）切成很多 TxT 小块，一块块喂给这台机器。  
3. **用时间 / 硅片成本说话**：同样算法，**时钟越快越省时间**；**T 越大越快，但芯片越贵**（晶体管大概按 T³ 涨）。

和「在电脑上调 OpenBLAS / 在显卡上调 CUDA / 用 Ollama 跑 Gemma」对比时，我们关心的是：

- 算完一个中等/大矩阵要多久？  
- 若把大模型「每个字」的算力预算都丢给这台机器，理想情况下能不能进毫秒级？  
- 做成硅片大概有多「重」（晶体管数量级）？

**一眼结论（理想满载、只比算力）：**

| 你想知道的 | 人话答案 |
|------------|----------|
| 这是什么 | **ASIC 风格**矩阵乘加速器设计（可仿真验证），不是成品 NPU |
| 小矩阵（几十维） | 往往 **纳米～微秒** 级，眨下眼都算完了 |
| 1024×1024 | T=32、1 GHz 大约 **零点一两毫秒**；T=64 大约再快 **近 8 倍** |
| 2048×2048 | T=32、1 GHz 大约 **1 ms**；T=64 大约 **零点一两毫秒** |
| 对标 Gemma 27B「出一个字」 | T=32 @1 GHz 理想大约 **几毫秒**；T=64 可到 **零点几毫秒**（仅计矩阵乘预算） |
| 芯片贵不贵 | T=32 ≈ **1.5 亿管**；**产品定档 T=64** ≈ **12 亿管**、die 约 **2 cm²**（不追 T=128） |
| 一片大概多少钱 | 先进工艺硅+封装 COGS 约 **$100～300**；独立芯片批发常见 **$200～500**（无 HBM） |
| 仓库里能跑什么 | **T≤32** 可生成 Verilog 并用 `vs` 仿真；**T=64 只做公式估算**（网表太大） |

下面先用「业务对照」展开，再给专业公式与假设，最后有一节总结。

## 一、业务视角：快不快、贵不贵、够不够用

### 1.1 两档「发动机」怎么选

把叶尺寸 T 想成发动机排量：越大马力越猛，油耗（硅片）也越高。

| 档位 | 乘法器数量 | 芯片「体重」（约） | 适合怎么理解 | 本仓库 |
|------|----------:|------------------:|--------------|--------|
| **T≤32**（量产讨论档） | 最多约 3.3 万个 | 约 **1.5 亿** 晶体管 | 塞进手机/边缘 SoC 里的一块专用加速器 | 可生成、可仿真 |
| **T=64**（**产品定档** / 纸面旗舰） | 约 26 万个 | 约 **12 亿** 晶体管，die ≈ **2 cm²** | 接近「整颗手机芯片」投资，换约 **8×** 速度；**不再往 T=128 加档** | 只估算，不入库巨型网表 |

经验法则（给非硬件同学）：

- **时钟翻倍 ≈ 时间减半**（同一套电路）。  
- **T 从 32 提到 64 ≈ 时间变为约 1/8，芯片逻辑大约贵 8 倍**。  
- **T=128** 还能再快约 8×，但硅片再贵约 8×——头脑风暴结论：**性价比停在 T=64**。

推荐讨论时钟：**500 MHz～1 GHz（ASIC/NPU 基线）**；100 MHz 仅作 FPGA 原型对照，不是上限。

#### 相对 OpenBLAS（CPU）/ cuBLAS（GPU CUDA）：快多少

用上表区间 **中位** 去除本引擎 @1 GHz 时间，得到约数加速比（越大 = 本设计越快）：

| M | vs OpenBLAS · T=32 | vs OpenBLAS · T=64 | vs cuBLAS · T=32 | vs cuBLAS · T=64 |
|--:|-------------------:|-------------------:|-----------------:|-----------------:|
| 64 | ~300×（12.5 µs÷40 ns） | ~2000× | ~200× | ~1400× |
| 128 | ~200×（60 µs÷0.29 µs） | ~1500× | ~90× | ~700× |
| 256 | ~60×（125 µs÷2.2 µs） | ~400× | ~20× | ~150× |
| 512 | ~30×（0.55 ms÷17 µs） | ~250× | ~4× | ~30× |
| **1024** | **~40×**（5.5 ms÷133 µs） | **~300×** | **~4×**（0.55 ms÷133 µs） | **~30×** |
| **2048** | **~30×**（30 ms÷1.06 ms） | **~200×** | **~3×**（2.8 ms÷1.06 ms） | **~20×** |

结论（理想满载、数据已在片上）：

- **对 CPU BLAS（OpenBLAS / MKL 同类）**：中大矩阵通常 **快约 30×～300×**（T=64 可到数百倍）。
- **对 GPU cuBLAS（CUDA）**：T=32 大约快 **3×～4×**；T=64 大约快 **20×～30×**（仍是我们更快）。注意 2048 的倍数（~20×）会比 1024（~30×）**略小**——见下节，单叶按 N³ 涨得比 GPU 更陡。
- 真机还有 PCIe/驱动/启动开销；即便打折，专用叶阵列仍可明显快过通用 BLAS/CUDA。若要 N 越大优势越大，需用 **1.2.2 并行分解**。

### 1.2.1 为什么 N 越大，相对加速比看起来「变小」？（例如 2048 对 cuBLAS 仍是 ~20×）

先对齐含义：**~20× 仍是我们更快**（cuBLAS 更慢），不是我们更慢。  
你直觉里「N 变大，优势应该变大」，对 **单叶串行** 不成立；对后面的 **分块并行分解** 才成立。

#### 算一笔 1024 → 2048 的账（T=64 @1 GHz vs cuBLAS 中位）

| | 1024 | 2048 | 变大倍数 |
|--|-----:|-----:|--------:|
| 本引擎（单叶 T=64） | 17 µs | 133 µs | **×7.8**（接近 2³=8，因为延迟 ∝ N³） |
| cuBLAS 中位 | 0.55 ms | 2.8 ms | **×5**（大矩阵上 GPU 更接近满血，没按满 N³ 那么陡） |
| **加速比（cuBLAS÷我们）** | **~32×** | **~21×** | **变小了** |

原因就一行话：

> N 翻倍时，我们单叶时间约涨 **8 倍**，而 cuBLAS 往往只涨 **约 5 倍** → 相对倍数被「摊薄」。

小 N 时加速比特别夸张，还有另一层：CPU/GPU **固定启动开销** 占比大；N 大之后这笔开销可忽略，倍数更接近「纯算力比」，所以表上会从几百倍掉到几十倍——这是分母结构变了，不是公式算错。

#### 怎样才能让「N 变大、相对优势也变大 / 延迟更线性」？

上 **1.2.2 的分块并行分解**：延迟 ∝ N，而不是 ∝ N³。

| N | 单叶 T=64 vs cuBLAS | **分解并行 vs cuBLAS**（T=32 叶阵列 @1 GHz） |
|--:|--------------------:|---------------------------------------------:|
| 1024 | ~30× | **~4000×**（cuBLAS 0.55 ms ÷ 0.13 µs） |
| 2048 | ~20× | **~1 万×**（2.8 ms ÷ 0.26 µs） |

这里 N 变大后，**相对 cuBLAS 的倍数是变大的**——因为我们时间只约 ×2，cuBLAS 仍约 ×5。

### 1.2.2 专门的分解电路：单步扫完一层 k（延迟 ∝ N）

思路：大矩阵仍切成 TxT 小块，但 **同一层 k 上，所有输出块 (ti,tj) 一次性并行算完**，再换下一层 k。

```
现在（单叶串行）：
  for ti, tj, tk:  leaf(A[ti,tk], B[tk,tj])   → 约 NT³ 步

分解加速（NT×NT 叶阵列，一层 k 一步）：
  for tk:                                    → 约 NT 步（∝ N）
      广播 / 并行加载 A[*][tk]、B[tk][*]
      所有 (ti,tj) 叶同时：acc[ti,tj] += A[ti,tk]·B[tk,tj]   // 「单步搞定这一层」
```

| 方案 | 延迟（拍数，约） | 随 N 怎么变 | 叶引擎个数 | 乘法器（T=32） |
|------|------------------|------------:|----------:|---------------:|
| 单叶串行（现仓库） | `≈ 4·(N/T)³` | **∝ N³** | 1 | 3.3 万 |
| **分块并行分解** | `≈ 4·(N/T)` | **∝ N（线性）** | `(N/T)²` | `(N/T)² × 3.3 万` |

具体数值（T=32，每层 k 按 4 拍计，@1 GHz）：

| N | 单叶串行 | **分解并行** | 约快 | 需要叶数 | 约乘法器总数 |
|--:|---------:|-------------:|-----:|--------:|-------------:|
| 128 | 0.29 µs | **0.02 µs** | ~16× | 16 | ~50 万 |
| 256 | 2.2 µs | **0.03 µs** | ~64× | 64 | ~210 万 |
| 512 | 17 µs | **0.07 µs** | ~256× | 256 | ~840 万 |
| 1024 | 133 µs | **0.13 µs** | ~1024× | 1024 | ~3400 万 |
| 2048 | 1.06 ms | **0.26 µs** | ~4096× | 4096 | ~1.3 亿 |

要点：

- **延迟**：从立方降到近似线性 —— N 翻倍，时间大约只翻倍（上表 1024→2048：0.13 µs→0.26 µs）。  
- **硅片**：叶数量按 `(N/T)²` 涨；对固定最大 N_max，可以按 N_max 一次铺满，小 N 时部分关断。  
- **和「尽量单步」的关系**：每一拍（或很少几拍）完成「当前 k 上全体输出 tile 的更新」；整次 GEMM 只要扫 **NT 个 k**，不再扫 NT³ 个 (ti,tj,tk)。  
- **晶体管**：1024 规模并行分解大约 **数千万～亿级乘法器**，比单叶 T=32（~150 M 管，含加法等）更重，但是用面积换 **线性延迟**；相对「直接铺满 1024³ 个乘法器一拍算完」仍便宜得多。

电路块（纸面模块划分，可后续单独做 RTL）：

| 模块 | 作用 |
|------|------|
| `tile_leaf[ti][tj]` | 现有 `gemmT_mac_array` + 局部 acc |
| `k_broadcast` | 每拍把 A 的第 tk「列块」、B 的第 tk「行块」送到各叶 |
| `decomp_ctrl` | 只扫 `tk=0..NT-1`，发起并行 LOAD/LATCH/ACCUM；最后并行 STORE |
| `c_mesh` | 输出 tile 写回总线（也可与下一层 k 双缓冲） |

这样 **N 变大时速度变差接近线性**；相对 BLAS/CUDA 的加速比也不会再随 N 立方塌下去（理想满载下，我们延迟 ∝N，算量 ∝N³，等效吞吐仍可维持高位）。

### 1.2.3 提前按 T=64 把 N=1024 组织好再 tiling——会更快吗？

**可以，而且值得做。** 这叫 **预分块 / packing**（和 OpenBLAS 的 packing、卷积里的 im2col 是同一类事）。

#### 怎么组织

把 1024×1024 在内存里先排成 **16×16 个 64×64 小块**（因为 `NT = 1024/64 = 16`），例如：

```
物理地址顺序（示意）：
  tile(0,0) 的 64×64 个元素连续存放
  tile(0,1) …
  …
  tile(15,15)
```

算的时候不再从「行主序大矩阵」里东拼西凑，而是：

```
for tk:
  直接 DMA / 总线突发读入 A 的列块面板、B 的行块面板（已是 64×64 对齐）
  喂给叶（或 1.2.2 的并行叶阵列）
```

#### 会不会更快？

| 层面 | 预分块有没有加速 | 说明 |
|------|------------------|------|
| **乘加次数** | 否 | 仍是约 `1024³` 次，算量不变 |
| **理想 RTL（本仓库拍数模型）** | 几乎不变 | 模型已假设「一拍并行写满整个 tile」，没计 DRAM 乱序代价 |
| **真实 ASIC/DRAM/总线** | **会更快** | 连续突发读、对齐 64×64，带宽利用率高、地址生成简单、可双缓冲下一 tile |
| **和 1.2.2 并行分解一起** | **更划算** | 每层 k 广播的数据本来就是整块面板，预分块后「单步搞定一层 k」更好实现 |

数量级直觉（真实系统，不是纯拍数公式）：

- 若不预分块：每个 64×64 可能要很多次 gather（跨步读），有效带宽可能只有峰值的一小部分。  
- 预分块后：接近顺序读，LOAD 墙钟往往能接近总线峰值 → **端到端常能再抠出一截**（常见经验是明显快一截，具体取决于内存子系统；算力瓶颈时收益变小）。  
- 预分块本身要付一次 **O(N²) 重排**（或上一层算子直接按 tile 写出，把重排摊掉）。

#### 和「T=64 叶」的关系

| 做法 | 作用 |
|------|------|
| 叶用 T=64 | 算得猛（乘法器多），单叶串行仍 ∝ `(N/64)³` |
| 数据预分成 64×64 | **喂得顺**，不减少叶调用次数，但减少每次喂数的浪费 |
| 预分块 + 并行分解（1.2.2） | 既喂得顺，又把延迟打成 **∝ N** —— 大 N 时这才是「越做越值」的组合 |

**结论：** N=1024 按 T=64 **提前 tiling 好再算，可以、也应该**；它让数据通路更接近「单步进叶」，在真实芯片上通常更快。若只看本仓库理想拍数表，数字几乎不动；若看产品延迟，预分块是标准加分项。

### 1.2.4 N=1024 展开成 T=64 叶：逐步过程

固定：`N=1024`，叶边长 `T=64`，块数 `NT = N/T = 16`。

1. **切块**：`A/B/C` 都看成 **16×16 个 64×64** 小块；块下标 `ti,tj,tk ∈ {0…15}`。  
2. **数学**：`C[ti][tj] = Σ_{tk=0}^{15} A[ti][tk] · B[tk][tj]`（块乘再累加）。  
3. **（可选）预分块**：内存里把每个 64×64 排成连续面板（见 1.2.3）。  
4. **单叶串行**（本仓库现模型）：

```
for ti, tj in 0..15:
    acc ← 0
    for tk in 0..15:          # 每个输出块沿 K 累加 16 次
        LOAD  A[ti][tk], B[tk][tj]   # 理想 1 拍写满整 tile
        LATCH / ACCUM                # 叶做完 64³ 乘加
    STORE C[ti][tj]
```

| 量 | 值 |
|----|---:|
| 叶调用次数 | `NT³ = 16³ = 4096` |
| 约总拍数 | `NT²·(2+4·NT) ≈ 16896` |
| @1 GHz | ≈ **17 µs** |

5. **并行分解**（1.2.2，纸面）：铺 `NT×NT=256` 个 T=64 叶，只扫 `tk=0…15`（延迟 ∝ N）。

```
1024×1024 → 16×16 个 64×64 →（预分块）→ 喂 T=64 叶
              单叶 4096 次  /  并行分解只 16 层 k
```

### 1.3 和大模型「出一个字」比什么？

用 Ollama 跑 Gemma，用户感受到的是：**每个字（token）要等多久**。  
背后算力粗算（只谈数量级，不是实验室实测）：

| 模型（常见档） | 每出一个字，大约多少计算 | 换算成本设计的大方阵 |
|----------------|--------------------------|----------------------|
| Gemma 2 **27B** | 大约几十 GFLOP（中位按 ~30 G） | 大约 **2 次** 2048×2048，或十来次 1024×1024 |
| Gemma 4 **26B-A4B**（MoE，激活少） | 大约 ~8 G | 大约 **半次** 2048×2048 |
| Gemma 4 **31B** | 大约 ~40 G | 大约 **2～3 次** 2048×2048 |

若假设「这些计算都能喂满本加速器」（理想情况，忽略 Softmax、显存、量化等）：

| 业务场景 | T=32 @1 GHz | T=64 @1 GHz | 你在 Ollama+GPU 上常听到的量级 |
|----------|------------:|------------:|--------------------------------|
| 做完一次 1024×1024 | ~0.13 ms | ~17 µs | GPU 库也常是亚毫秒～1 ms |
| 做完一次 2048×2048 | ~1.1 ms | ~0.13 ms | GPU 库大约 0.5～5 ms |
| **27B 档 · 出一个字** | **约 1.5～3.5 ms** | **约 0.2～0.4 ms** | 常见大约 **20～80 ms/字**（看显卡与量化） |
| **A4B · 出一个字** | 约 0.5～1 ms | 约 0.06～0.15 ms | 往往更快（激活参数少） |
| **聊一段话（上百字）** | 还要 ×字数 | 同样 ×字数 | GPU 也是秒级对话，但更吃并行与带宽 |

人话版：

- **单字延迟**：T=32 已经能和「中端本地大模型」用毫秒语言比；T=64 更激进，纸面上可到亚毫秒。  
- **整段回答**：字一多，时间就线性变长——要再快，不能只靠一块叶，而要多块一起干或上真 GPU。  
- 上表 **不是** 说本仓库已经能替代 Ollama；而是说：**若把同类算力预算丢给这种架构，时间落在哪一档。**

### 1.4 芯片贵不贵（晶体管、die、成本与售价）

| 方案 | 大约多重 | 怎么跟日常比 |
|------|----------|--------------|
| T=32 叶引擎 | ~**1.5 亿** 晶体管 | 像手机里「一块很认真的 AI/多媒体加速器」 |
| **T=64（定档）** | ~**12 亿** 管，die ≈ **2 cm²**（~14×14 mm） | 接近「整颗手机主芯片」投资；先进工艺密度下 **2 cm² 装得下** |
| T=128（不追） | ~**10 亿量级×8** 逻辑 | 再快约 8×，硅片再贵约 8×——头脑风暴结论：**性价比不划算** |
| 一颗手机 SoC | 约 100～200 亿 | 整机大脑 |
| 大型独立 GPU | 数百亿起 | 桌面/服务器显卡 |

钱（硅片）几乎都花在 **密密麻麻的乘法器** 上；缓存反而相对不占。

**规格直觉（T=64 单叶逻辑核）：**

| 项 | 量级 |
|----|------|
| 裸片 | ≈ **200 mm²**（2 cm²） |
| 封装 | 手机式 SoC 约 **12–15 mm** 边；独立 BGA 常 **20–30 mm** |
| 功耗 | 满转可到数十瓦；门控/降频后消费级可压到数瓦～十几瓦（取决于用法） |

**成本 / 售价（无 HBM、量级估算，非报价）：**

| 层 | 大约 |
|----|------|
| 先进工艺晶圆 | N5/N4 约 **1.6～2 万美元 / 片**（公开分析师量级） |
| 硅 + 封装测试 COGS | 约 **$100～300 / 片**（良率正常、大批量） |
| 芯片批发（独立加速芯） | 约 **$200～500** |
| 零售模组 / 小卡 | 约 **$400～1000** |
| 带 HBM 的服务器卡 | **数千美元起**（贵在内存与先进封装，不是这 2 cm² 逻辑本身） |

小批量时还要摊 **设计 NRE**（先进节点整 SoC 常说数亿美元量级），出货少则每片摊销会远高于上表 COGS。

## 二、专业细节（给要核对数字的人）

### 2.1 结构与公式

```
C = A · B
叶：gemmT_mac_array —— T³ 路乘法，1 拍锁存结果
分块：C[ti][tj] += mac(A[ti][tk], B[tk][tj])，ti,tj,tk ∈ [0, NT)，NT=M/T
一拍并行写入整个 A、B tile；一拍读出 C tile

N_cyc ≈ NT² · (2 + 4·NT)
t     = N_cyc / f_clk
FLOP  ≈ 2 · M³
主导：时间 ~ M³/T³；T↑2 倍 → 时间 ~÷8，乘法器 ~×8
```

可运行生成：

```bash
python3 tools/fpga_gemm3/gen_mac_array.py --all
python3 tools/fpga_gemm3/gen_tiled.py --matrix 1024 --tile 32
python3 tools/fpga_gemm3/gen_tiled.py --matrix 8 --tile 4 --demo
# 单叶 demo → ctest sim.fpga_gemm3；分块 demo → sim.fpga_gemm8_tiled
```

总线演进（同一 1024³、仅比搬运）：逐元素 → 按行 → **整 tile 并行**，延迟可降约两个数量级；再叠提频与 T=64。

### 2.3 晶体管估算假设

| 部件 | 单价（约） |

## 三、总结

1. **做什么**：按 **ASIC 风格**（固定乘法器阵列 + 大矩阵分块）讲清 AI 里最核心的矩阵乘，如何在硅片上权衡「快」和「贵」。  
2. **产品定档**：**T=64** 为纸面旗舰（~12 亿管、die ≈ 2 cm²、COGS 约百～三百美元量级）；**不追 T=128**。想省硅用 T=32（大约慢 ~8×）。  
3. **普通人怎么记**：想快 → 提主频 / 加大 T（到 64）/ 多放叶；大 N 再叠加 **预分块** 与 **分块并行分解**（延迟 ∝N）。  
4. **业务体感**：1024/2048 级矩阵乘可到 **亚毫秒～毫秒**；Gemma 27B 档「单字」算力预算理想下也可落在 **毫秒甚至亚毫秒**，但整段聊天仍要 × 字数。  
5. **本仓库定位**：**T≤32 可仿真**；T=64 与成本/die 讨论是 **ASIC 规划外推**。目录名 `fpga_gemm3` 保留；叙事以 ASIC/NPU 为准。  
6. **下一步若更贴大模型**：矩形 GEMM、分解阵列落地 RTL、与 Attention 专用通路。
